# C99: Task 14's rulings

*Recorded 2026-10-28, coordinator.* · [Decision log](README.md)

## Decision

(1) Task 14's own guards, which the plan lists without ids, are named L3.HS (the history scan), L3.PR (the public-ready file), L3.N (the notices) and L3.S rows, prefixes no other task or the plan uses; L3.H and L3.P stay with the plan's rows. (2) Task 14 also writes `scripts/build-mermaid.mjs`, its `.d.mts` and `test/mermaid-bundle.test.ts`, which the shared-files table gives to Tasks 4, 6 and 13: THIRD-PARTY-NOTICES must be generated from the metafile of both Mermaid builds and cover the runtime libraries, which needs the generator to bundle the frame build too and write a second section. The table gains Task 14 as a writer of those three files, and deferred Task 13 builds on that generator. (3) Accepted from the review: `ci.yml`'s concurrency group names the calling workflow (`ci-${{ github.workflow }}-${{ github.ref }}`), so the release's test job never waits behind main's own CI; verify-tag requires the fetched tag, the checkout and the pushed commit to peel to one commit, so every later job builds exactly the commit whose signature was checked; the history scan lists every ref the remote advertises and reads those outside branches, tags and pull requests too (notes and any other namespace), failing closed on an answer it cannot parse, and reads each pull request's head and base branch names; github-release refuses a malformed prerelease flag, as publish does; the one `private` pin is searched for in every form under all of `test/`. (4) verify-tag grants `actions: read` to read the `npm-release` environment, per the platform's documentation; only a tag run reaches that check, so it is unmeasured until v1 and fails closed if wrong. (5) For the operator, before Task 15 step 2. The plan has the operator push the signed tag and be the environment's only required reviewer with self-review prevented, and the platform refuses that approval, so the publish gate cannot be passed except by an administrator bypass. One of three must be ruled: (a) a second required reviewer who does not push the tag; (b) a different identity pushes the tag; (c) self-review allowed for a single-maintainer lane. Whichever is chosen, the environment check then also requires that administrators cannot bypass, with its own test and mutation rows. The coordinator recommends (c), because the signed tag already proves the maintainer's intent and the approval is a second deliberate act by the same person. Also the operator's: the `maintainers` team that CODEOWNERS names does not exist in the organisation and must be created with write access, or another owner ruled, before a ruleset requires code-owner review (the platform ignores a rule whose owner it cannot resolve); private vulnerability reporting must be on for SECURITY.md's link; the scan does not read title-rename history, past Actions logs and artifacts, discussions or the wiki, so those are reviewed by hand before the visibility change; and the scan's error lines can echo git's or gh's stderr, so its output is read before it is shared.

## Why

Each fix closes a gap between what goes public or gets built and what the lane checks.

## Cost if wrong

A lane that refuses a good tag, which is the safe direction.
