# C90: Task 5's rulings

*Recorded 2026-10-27, coordinator.* · [Decision log](README.md)

## Decision

(1) The frame's pacer holds a message until the oldest of the last 16 is more than 1,100 ms old: the plan's 1,000 ms window plus a 100 ms transit margin, measured on a monotonic clock. A strict sliding window read on arrival times refused messages under the plain 1,000 ms window (two bursts sent just over a second apart can arrive closer), so FD11's "neither reading ever refuses it" holds only while transit jitter stays within the margin; no pacer can promise more against unbounded delay. L3.M12 now feeds both readings jittered arrivals (0 to 99 ms) and both refuse nothing. FD11, Reference §8.4 and the row are amended. The margin is the frame's own constant (`outbox.ts`); the consumer's parser does not need it. (2) The bootstrap is built fully minified (25,593 bytes against its 32 KiB budget), with Task 3's `validateSeed` check reading the build's input list instead of the minified names. (3) L3.B6a, ready before Mermaid's first full pass, must go red deterministically: the row records the reader's drawing state at the instant the frame posts `ready`, through test-side instrumentation in the frame's realm, never through shipped bytes. (4) Accepted deviations: the guard reads no `Function.prototype.toString` (it never uses it); the content vocabulary adds the conformance oracle's tag list to what the corpus emits, because the corpus has no h4 to h6; the outbox also exposes `copy`, `changes`, `answer` and `dispose`; the frame relies on the layout's own validation of a `changes` reply instead of importing it into the size-limited bootstrap. (5) Mermaid's frame file writes `fastdom` and `injected`, so Task 6's free-global list must leave those two unpinned (a pinned name is read-only and Mermaid's write would throw); the two it reads lazily are pinned. (6) Task 5 also edited `test/frame-document.test.ts` (Task 3's) and `scripts/build-frame.d.mts` (Task 6's) for the minified build.

## Why

Each is the closest faithful reading of the plan that the measured behaviour allows.

## Cost if wrong

A parent with more than 100 ms of jitter that reads the limits as a strict window can still refuse; the bucket reading the plan prescribes does not.
