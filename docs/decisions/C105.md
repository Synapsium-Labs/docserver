# C105: The batch runs as one wave on one branch and one PR

*Recorded 2026-11-04, coordinator.* · [Decision log](README.md)

## Decision

The batch plan's "How this wave runs" said each task is its own branch and PR, merged in dependency order, with a scratch merge before each group. The coordinator runs it instead as one ccrc wave: one worker, one workspace branch, one PR. (1) The tasks land as commits in the table's order, 1 to 9, which meets every "Depends on"; the "Group" column now only orders the commits, and the scratch merge falls away. (2) Each task still runs as the plan says: an implementer subagent, tests first, a held-out panel of three lenses, a refute pass per finding, one fix round, and its Verify green before the next task starts. (3) The coordinator's review run reads the whole branch once Task 9 is committed, and the PR merges only after it. (4) No rebase or force push ([C55](C55.md)). (5) The signed tag stays the operator's act after the merge.

## Why

A ccrc run's done fingerprint measures one workspace branch, so nine PRs would mean nine runs, nine review runs and nine merge round trips, and the dependency chain leaves little to run in parallel (Tasks 4 and 6, and 5 and 8, at most).

## Cost if wrong

One large PR to review; each task's commits and its own panel keep it readable, and the release waits for every task either way.
