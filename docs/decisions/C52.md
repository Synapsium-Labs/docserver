# C52: Task 8 as built, and the merge order within a group

*Recorded 2026-10-20, coordinator, from L2 Task 8's review.* · [Decision log](README.md)

> [!NOTE]
> Amended by [C55](C55.md); read them with this one.

## Decision

- **The three lists [C48](C48.md) left open:** `rulingHeaders` and `attention.openStatus` are options, because they read status and header words, which are options. `decisionHeaders` stays format contract, beside the technical header words.
- **A whole word is whole in any script.** The lists read as whole words compile per word, with Unicode-aware lookarounds and the `u` flag, in place of the reference's ASCII `\b`. Before, a word with a non-ASCII edge, or one ending in punctuation, could never match. This departs from the reference: "Doneé" opens no status, and the default ID scan finds no ID that touches a non-ASCII letter. A feature that copies one of these patterns keeps its flags (`new RegExp(re)`), never its `source` alone.
- **The item link departs from the reference on purpose.** It uses the class `item-link`, leaves an author's own link alone, writes at most 64 links, and routes their clicks through one listener on the byline.
- **Task 8's edits outside its writers list stand:** two option rows in `README.md` (Task 5's guard requires a row per option), one line of `test/enhance-options.test.ts`, and two expectations of `test/enhance-seams.test.ts` that had pinned the defect above.
- **A `live()` check after a host call-out stays even when no case can redden it.** LD5 requires one after each await, so its row is reported green (Task 8's M123, M124 and M186). A check that is neither a plan rule nor measurable is still dropped ([C49](C49.md)).
- **Carried to Task 14:** export `VocabularyOptions` by name, with [C47](C47.md)'s types. **Carried to Task 24:** the README text in Task 8's PR body: the namespaced storage keys, the item link's row, the vocabulary table, and the "nothing to act on yet" sentence. Task 14 still updates the `pos` row ([C48](C48.md)).
- **Merge order within a group:** a group's tasks merge in the order their reviews finish, each rebased onto `main`; disjoint files keep that mechanical. The task table's order binds across groups only, so a task starts once its "Depends on" tasks have merged.

## Why

Each follows the code the review measured, or keeps a finished task from waiting on a slower neighbour.

## Cost if wrong

A feature that rebuilds a pattern from its `source` alone loses Unicode matching. The reviews of Tasks 9, 11 and 13 check for that.
