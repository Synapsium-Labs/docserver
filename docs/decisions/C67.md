# C67: Rail follow and reader work may use separate frames

*Recorded 2026-10-23, operator timing choices, bounded coordinator contract.* · [Decision log](README.md)

## Decision

The operator approved delaying pending spy/bar work on a rail-follow frame, then approved delaying a conflicting whole relayout while keeping its measurements, position restoration and public event together. This changes follow/update timing only; numerical bounds and exact live geometry remain unchanged.
- **One per-root queue:** `env.ts` may own a lazy root-keyed internal queue, registered and cleaned up by `createEnv`, with a bounded internal scheduling export for `relayout`, `spy` and `rail` jobs. Unknown or non-live roots do nothing; no independent fallback, document-global scheduler, public API, `Env`/context interface or lifecycle change. Use the existing environment frame/cancel/liveness spine. Keep one physical callback and at most one pending callback per category; consume an entry before invoking it. Reader work and rail follow alternate when both are pending, with relayout preferred over a pending spy. No starvation under continuous scroll. Keep the queue busy through the whole transaction; requests during it wait. Schedule subsequent work only in completion `finally`, preserving callback errors. Cancels remove only their exact entry, and cleanup deletes the registry only if it still owns that queue instance.
- **Atomic relayout stays atomic:** only its scheduling changes. Preserve reason coalescing, root-width startup samples, measuring-listener order, synchronous bar-height update, `position.keep` restoration, fault propagation and public event order. Uncontended work still runs next frame; on a rail conflict, the whole transaction waits. Scroll's relayout listener still runs `reshow()` and `spy()` synchronously; at entry it clears and cancels only the exact previously pending redundant spy. A reentrant new scroll request must survive. Every relayout/spy entry path uses the common queue, so already queued callbacks cannot combine rail geometry with reader work in one physical frame.
- **Exact live rail follow:** active/ARIA/open state changes synchronously when the spy payload is emitted; follow is deferred and the latest target replaces earlier pending follow. Validate liveness, exact active identity, connection/root ownership, Contents selection/hidden state and drawer state before geometry and after each geometry call-out. Keep the anchor's box-safety check and read the live anchor and panel bounding rectangles. A nonzero panel bounding height supplies the panel guard. Follow only when `link.top < panel.top + 60` or `link.bottom > panel.bottom - 60`; equality at an edge alone does not trigger. Add `link.top - panel.top - panel.height / 2` to that panel's `scrollTop`, centering the link's top subject to native clamping. Read `scrollTop`, revalidate after its getter, then assign; no subsequent forward work after invalidation. Do not substitute `clientHeight`, cached/offset geometry, native nearest scrolling, replacement-target lookup or viewport movement. Exceptions keep their existing propagation.
- **Narrow shared-test dependency:** the direct `createRelayout` fixture constructors in `test/enhance-relayout-baseline.test.ts`'s `scene`, the services position-keep/fonts-timeout case, and `test/enhance-services.test.ts`'s `fakeRelayout` may register the real queue using a real journal and `createEnv`. Make only the browser frame boundary deterministic, honor cancellation and restore owned descriptors. Existing computed/observer/fonts inputs may remain test-only wrappers; no fake queue or production test hook. Preserve all width/unknown/equal/change, event-order, keep, listener-error/destroy/cancel and fonts assertions; journal cleanup owns each fixture's actual queue.
- **Per-frame evidence, not hidden work:** the existing no-task `ceil(log2(n + 1)) + 2` and general `2 * ceil(log2(n)) + 4` bounds stay. The two no-task unit RF3 cases may replace cumulative waiting with physical-frame buckets that count both rectangle APIs and every resulting callback through settlement, reporting cumulative work too. Keep selection/unit assertions and all real features. Dedicated queue/rail controls cover small and large documents, continuous scroll, all request orders, relayout conflicts, reentry, exceptions, exact-entry cancellation, replacement-root cleanup, removal and destroy/rollback. Browser controls pin strict 60 px edges, fractional/transformed live geometry, manual panel scroll, link-top centering and panel-only movement. Count the whole single-root fixture, never exclude rail or move work outside the measurement window. This establishes neither a universal logarithmic relayout bound for plan-unit box scans nor a multi-root aggregate budget; sibling isolation remains mandatory.
- **Source release remains separate:** only `env.ts`, `relayout.ts`, `scroll.ts` and `rail.ts`, dedicated tests and the named shared-test regions are candidates for a later TDD writer brief. Genuine assertion reds precede edits, semantic reversals and restored controls follow, then both browsers, unchanged walls/import controls, all TypeScript projects and a full named-failure census. No CSS, scanner, corpus/golden, state, journal, lifecycle, context, public interface or feature-order change is authorized. Independent contract review found the amended approach viable in principle, not implemented; its actual model does not waive any required-model gate. No Task 18/19, combined-group or RF3 acceptance follows.

## Why

The live rail reads exceed a budget already consumed by the search and bar, and native nearest scrolling differs from the reference's edge-band centering.

## Cost if wrong

Conflicting updates become less frequent; atomic relayout, complete frame accounting and live geometry prevent that tradeoff from silently changing position, hiding work or using stale measurements.
