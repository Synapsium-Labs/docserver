# C69: Acceptance uses bounded existing tools, not another repository-copy campaign

*Recorded 2026-10-25, coordinator.* · [Decision log](README.md)

## Decision

The operator prohibits further disk-intensive exercises. This changes execution mechanics, never the required outcomes:
- Task 24 may replace the pack test's recursive checkout copy with selective package staging or bounded in-memory compiler/build output. It must still exercise an actual packed consumer through package-name exports, strict declarations, Mermaid resolution and the existing missing-type/corrupt-corpus negative controls. Dependencies are reused, not copied or installed. A manifest-only inspection is not equivalent acceptance.
- The existing visual runner may gain bounded artifact controls. Every required neutral sample, viewport, preference and interaction state still gets its geometry/computed-style comparison at the unchanged 0.1 px tolerance. Measurements may be compared in memory and only differences retained; a small inspected screenshot set remains part of the visual check. No broad screenshot collection, weakened tolerance or hidden unmatched component is authorized.
- Existing CI remains the Node 22/24 and both-browser acceptance environment. Local Chromium evidence is named as such; cached WebKit currently fails startup because system libraries are absent, and no install or container fallback is authorized. No full-suite or release claim precedes actual successful verification.

## Why

Copying a checkout and accumulating images are implementation choices, not quality guarantees.

## Cost if wrong

A replacement path could miss packaging or visual defects; the preserved positive and negative outcomes and independent review remain mandatory.
