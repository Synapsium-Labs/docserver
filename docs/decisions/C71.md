# C71: The feature-registration control accepts the completed layout, not a permanent stub

*Recorded 2026-10-25, coordinator.* · [Decision log](README.md)

## Decision

The existing seams test requires at least one registered module to retain its stub header, so filling the last modules necessarily makes that control red. Its per-module assertions remain: every module is registered, exports build and after as declared, and carries either the exact stub header or its implementation task. Remove only the obsolete positive-stub-count assertion. The filled Changes since and diagram-tools headers name Tasks 22 and 23 respectively. Resolve the asynchronous feature-module list before taking the separate stub no-op DOM snapshot: importing the list after the snapshot lets normal scheduled reading work change the DOM even when the list has no stubs. The no-op equality and all per-stub assertions remain. No runtime behavior, feature ordering, scanner or other test assertion changes.

## Why

A prototype-progress check cannot demand unfinished implementation in the final package.

## Cost if wrong

A newly unmarked module might pass; the retained registration, export and exact header checks continue to reject it.
