# C94: Task 16's rulings

*Recorded 2026-10-28, coordinator.* · [Decision log](README.md)

## Decision

(1) With `mermaid.draw: 'on-request'` the first drawing comes after `ready`, so the bootstrap's violation listener could not see a host policy that blocks Mermaid's inline styles, and a partly working frame stayed mounted, against R7 and Reference §11.5. In that mode only, the bootstrap probes inline style once at boot with one `<style>` element and one `style` attribute (the two checks a drawing triggers), removed before `ready`; a blocking policy then fails closed as ready, then error, as it does in `'auto'`. The probe's one `style` attribute is the single named exception to "no style attributes in shipped code": it runs only where Mermaid's own first draw would set style attributes, so it asks the host for nothing the drawing does not. (2) Accepted: the browser file `test/browser/mermaid-on-request.test.ts` (not in the plan's list; it proves the new styles and a real tap); the per-figure states in `data-docreader-draw` (`on-request`, `busy`, `drawn`, `failed`) with `aria-busy`; `MERMAID_DRAW_VALUES` repeated in the layout, which cannot import from the frame, held equal to the seed's list by a type check and a runtime check; the additive page-policy option in the frame host page and the served-path record in the harness. (3) Task 12's README states the host duty that a host never loads a stock Mermaid with start-on-load on (the package's own Mermaid files have it off), and that a stylesheet-hash page policy serves only documents without Mermaid.

## Why

The on-request mode must fail the same way as `'auto'`.

## Cost if wrong

A host policy that allows the probe's checks but blocks some other style Mermaid uses would still leave a partial frame, which the README's policy requirement rules out.
