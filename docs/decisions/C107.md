# C107: Item B, Mermaid drawn after `ready`

*Recorded 2026-11-05, coordinator.* · [Decision log](README.md)

## Decision

BD1 to BD10 stand as built, and `'auto'` and `'on-request'` keep their exact behaviour. (1) BD1 to BD10: `'after-ready'` is one more value of the draw mode in every layer, under one name; `./enhance` sets no gate while it waits and the root reads `waiting` with readable sources; the build travels as `{t:'mermaid', text}` and is inserted as one inline script, `{t:'mermaid', unavailable:true}` being the host's "no build"; the bootstrap accepts a registration only from the element it inserted, once; `fastdom` and `injected` are reserved in the bootstrap's first phase in every mode; the inline-style probe runs in every mode but `'auto'`; `./host` checks the text against the manifest's Mermaid hash before posting and posts `unavailable` with one warning on a mismatch or rejection; a host that never hands the build over leaves the root `waiting` for the life of the mount; figures draw in `'auto'`'s order (BD9: every figure within one and a half screens of the reader in document order, then the rest by distance); a policy that blocks Mermaid's hash after `ready` leaves every figure as its source with the load note and sends no `error`. (2) The answers: Q2, the default stays `'auto'`; Q3, the name `'after-ready'`; Q4, "nearest first, reusing `'auto'`'s order", which is that order (BD9), so a figure in view can wait behind earlier figures up to one and a half screens away; Q5, the E17 risk is accepted with the gate's caps (24 fences, 16 KiB each) as the bound, and a figure-heavy document is measured on a phone in the first consumer's take-up wave; Q6, the degradation above is accepted; Q13, no frame-side timeout for the handover; Q14, one structured-clone copy of the build per Mermaid-on mount, the loader called once per `DocFrame`. (3) Departures, each accepted by the wave's controller during the task's review and ratified by the coordinator at review 1480. BX-1: typecheck-forced edits to a docstring and a type pin in Tasks 3 and 7's files. BX-2: the option conditional moved into `adapters.ts` as `mermaidOption()` and `arrivesLate()` so it is unit-testable, with `pin.ts`, `test/frame-build.test.ts` and the README's policy-hash quote touched. BX-3: a late registration is accepted only when exactly one `docserver:register` arrives during the insertion, its target is the inserted element and it carries `initialize` and `render` functions; any other count or target settles `load()` to null, the load note, a denial and never a substitution. BD4 says "only from the element it inserted, once", and a first-wins reading let a nested forged dispatch on the same element substitute an API; the decision is a pure helper (`lateApi`). (4) to (7) are the controller's task-level rulings, made during each task's review and ratified by the coordinator at review 1480, the equivalent-mutant calls among them. (4) Task 2: B2i and B2j (the two new `live()` guards in the after-ready branch) are equivalent mutants, since after destroy the journal refuses writes and `load()` answers null; they stay as defence in depth. (5) Task 3: the `unavailable` branch's red case is a Task 5 browser row. Parked: in-frame code that suppresses the real registration and dispatches exactly one forged one on the inserted element would still be accepted; only code already running in the frame can do that, and the policy admits only the frame's own four scripts, none of which does. (6) Task 4: when both `loadMermaid` and `assets.mermaid` are given, the loader wins; a non-function `loadMermaid` is checked only in `'after-ready'`; the verdict is held per `DocFrame`. B4s (the `sent` flag) and B4v (the hook cleared once used) are equivalent mutants, since no path posts twice; B4t (the try/catch around the checks) is containment, unreachable by test input (only an allocation failure while hashing an at-cap text throws there). (7) Task 5: BR1 is cleared: B5.1, a dynamically inserted inline script matching its hash, is green on Chromium and WebKit in CI (22 tests in `test/browser/mermaid-after-ready.test.ts`, 11 on each engine), so BD3's remount fallback is not needed. The two `onViolation` guards that predate the batch were each measured alone in fix round FR1 (review 1480, A9; `batch-mutations/task-5.md`). The `done` guard has a case of its own: B5.4b, a violation of another kind after ready (an image from another origin) leaves the frame alive and a prefs op still takes effect, and B5b5 (the guard dropped alone) is red through it. The blocked-inline exception alone (B5b6) is not an equivalent mutant: after ready the `done` guard returns first, but a blocked inline script's violation delivered before the bootstrap's DOMContentLoaded handler has run `start` would end the boot as `boot` instead of with the owning reason. Case B5.4c delivers it, and B5b6 is red through it (row B5b6s; review 1494, F2, [C113](C113.md)). B5b drops both guards together.

## Why

The plan's decisions and the controller's task-level rulings, in one place.

The stricter registration refusal can only be triggered by hostile in-frame code; the exception has a case of its own (B5.4c), and WebKit is CI's.
