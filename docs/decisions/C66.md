# C66: Service probes disable the real settings owner only when supplying its stand-in

*Recorded 2026-10-22, coordinator.* · [Decision log](README.md)

## Decision

This is a test-composition prerequisite exposed by the first [C65](C65.md) neighboring-control run, not a production exception or task acceptance.
- **Exact shared-test scope:** in `test/enhance-services.test.ts`, change only the startup options in the seven-overlay Escape-order case and the five-tool fixed-order case to `enhance(root, { chrome: { settings: false } })`. Both cases deliberately register their own settings stand-in; the real settings feature now owns that exclusive overlay/tool when enabled. These two fixture options already exist in Task 19's test version.
- Preserve every overlay/tool position, arbitrary registration order, duplicate and unknown-kind refusal, and assertion. Retain the corrected services file's other feature exclusions, plan-member/fingerprint controls, relayout dependencies, resize cases and CSS marker. Do not replace it wholesale with the older Task 19 version, disable settings globally, skip either case or weaken production registration guards.
- Establish the exact two-line patch and unchanged remainder before rerunning. Require both previously failing cases and the complete services file green, then resume the stopped neighboring/browser verification with all failures named. This adds no source, interface, harness, configuration, scanner, corpus, golden, navigation, RF3 or geometry change, and waives no required-model or full-suite gate.

## Why

A service probe's fake exclusive owner collides with the real feature rather than testing service behavior.

## Cost if wrong

Disabling the feature too broadly could hide an integration failure; the two local options and unchanged full ordering/refusal assertions keep that boundary explicit.
