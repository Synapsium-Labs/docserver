**Rail measurement (Chromium).** `source.width` was 348 under the expected `width - 388`, which is the shape of the code block measured as the reading column (704 px at 1440) instead of the wide width (1052 px). The wide width comes from the `long` class that the code feature writes on a relayout, and the relayout that follows the font load is queued for the next frame. The measurement ran between the rail's build and that relayout. The test now waits, before each measurement, for the state the page reports: the root has `has-toc`; from 1240 px, `--rail-w` is set and the rail is displayed; the first code block carries `long`; `document.fonts.status` is `loaded`; the window is at the requested scroll position. It then lets two animation frames pass (a frame boundary, not a timer) and waits for the same state again, so a relayout queued by the last change has run. `wideMetrics` has the same exposure (a perturbed run reproduces the failure as the same 348 on its 1440 case), so it waits on the same state too. Every existing assertion is unchanged.
